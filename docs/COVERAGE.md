## Reproduction

From the repository root, with Docker Desktop running:

```sh
python3 tools/coverage/run.py --work .local/coverage-final
```

This is the command used for the accepted generation. On a machine where that work directory already contains traces, use a fresh ignored work path (for example `.local/coverage-reproduction`) to regenerate everything. Existing run directories deliberately cause an error rather than mixing observations. `--resume --steps export` re-exports existing completed traces; a resumed test run checks the manifest and tracing-tool hashes. The runner verifies the source revision and a clean Git status before and after processing.

The official `sample/tests.json` must be present locally; restore it from the published starter when reproducing in a fresh clone, since sample datasets are intentionally ignored by Git. Answers and sample patches are not needed for generation.

The command fetches `https://github.com/tobymao/sqlglot.git` at exactly `eb11aec4be8cb2122afe713a4816662c3f0fb2fa`, detached, using a depth-one fetch. Source tree: `6606fc5229c882bd0cf8f9ba79503e9e10d084f7`. The checkout is read-only inside Linux containers. No sample patches are applied. It builds the separate `tools/coverage/Dockerfile` with the official base image digest and every exact package version in `requirements.lock`, adding only pinned `coverage==7.13.5`. The generator checks installed versions against every lock entry. Lock SHA-256: `4201e26c5e438697189dbfb809917eb8618d488a6926eee0f49858aad971d212`.

The runner performs tooling self-checks, full collection, four isolated pilots, a pilot context audit, full-manifest tracing, export, and independent reference validation. Test/collection failures remain in raw reports and the exported audit instead of silently discarding their tests; infrastructure/context-audit failures stop the pipeline. Each pytest invocation uses:

```text
--rootdir=/src -p no:cacheprovider --tb=short -q
--continue-on-collection-errors --timeout=600 tests
```

Collection adds `--collect-only`; a plugin selects exact node IDs after collection for pilots/full runs. The 600-second per-test limit is an offline tracing safeguard, not a claimed reproduction of any undocumented server per-test timeout. The raw logs and reports are under `.local/coverage-final/`; raw databases, checkouts, environments, logs, and the initial exploratory run stay outside Git. Only `tests.json` is mounted from the sample directory, never its patches or answers.

## Manifest identity and attribution

Manifest SHA-256: `21257a93c58f4b0646c5122586d2141b4b340ad85b2f0bb251af3746de3f0dc2`. It has 1,620 numbered tests across 58 files and one additional declared skipped node ID. Numbered entries contain `number`, `id`, `file`, and recorded `seconds`.

Match by the **exact pytest node ID**, independently verifying the relative file path. Node IDs contain path, class, method, and any parameter suffix; no mapping from collection position to test number is used. Every collected item in this pinned environment has a class/method identity, and no item has a pytest parameter suffix. The source's many `unittest.subTest` cases remain within their parent's numbered method. Both normal and subtest reports are captured through pytest's report hook; a failed subtest marks its parent incomplete even if the parent also reports a passing call.

SCORING.md guarantees contiguous numbers within an input manifest; it does **not** promise that a number identifies the same test in every future manifest. Internally, maps use a sorted table of canonical node IDs. Set offsets refer to that table, not official test numbers. `manifest_number` is historical provenance. Stage 4 must build a unique `id -> number` mapping from each incoming tests.json and resolve mapped identities through it. Duplicate or missing identities, differing files, or previously unseen tests require a conservative fallback; never reuse historical numeric IDs as answers.

Coverage starts before pytest import/collection. Each setup, call, and teardown phase has a distinct `test|<nodeid>|<phase>` context. Shared fixture setup/finalization receives separate fixture contexts. The fixture consumer closure includes static fixture dependencies and dynamically requested fixtures. Shared class setup and cleanup generated by pytest for unittest classes are included. Fixture lines are associated with every recorded numbered consumer, not only the first/last test.

The tracer instruments only the pinned `/src` repository, including `sqlglot/`, test methods, shared test helpers, and other repository Python files. Standard-library and installed third-party lines are excluded. Helper execution inherits its active caller context. Import/collection execution and execution between tests remain explicit global shared contexts. Multiprocessing, ordinary subprocesses, threads, and process exits are instrumented using coverage.py's supported process settings. All child-database observations are deliberately exported as **globally shared process execution**: a reused worker pool is not assumed to retain the identity of its current submitting test. This keeps child execution instead of incorrectly attributing it or dropping it.

The isolated pilots use parser union, executor array slicing, optimizer aggregate annotation, and executor TPC-H execution methods. The audit checks each test's own body ran under its call context, no other test identity appeared, all three phase hooks ran, collection succeeded, and the process-pool pilot saved child databases. Isolated observations supplement the full-run maps to retain additional cold-cache execution. When a phase executes no repository Python lines, its hook is still recorded; class fixture source execution appears under shared fixture contexts rather than being mislabeled as individual setup/teardown coverage.

The tooling self-checks separately validate shared setup and teardown ownership (including a dynamically requested fixture), range encoding/deduplication, and nested/decorated AST ranges. The fixture test caught an early implementation error: pytest binds finalizer callbacks before the setup hook. The corrected tracer wraps the fixture finish method before collection. Preliminary traces were discarded from the exported index, and the full pipeline reran in a new clean work directory. A subsequent export rejected one unreadable child shard at container shutdown. The generator now explicitly joins Python's resource tracker before PID 1 exits, and collection/pilots/full tracing reran again. Old traces remain under ignored `.local/coverage/` and `.local/coverage-final/raw-pre-cleanup/`; they do not contribute to the accepted index. These were tooling problems, not clean-source test failures.

## Artifact format

Three compact, deterministic, uncompressed plain JSON files live in `coverage_index/`:

- `index.json`: canonical test identities and their manifest correspondence/status; deduplicated `test_sets` and `shared_sets`; named `shared_contexts` and their fixture consumers; per-source-file content hash, line count, observed status, line-to-test coverage, and function/class ranges; class/file test cohorts for conservative cache/fixture widening. Semantics explicitly state that absent coverage does not prove safe exclusion.
- `audit.json`: manifest reconciliation, unmatched/ambiguous identities, declared/observed skips, collection/test failures, incomplete tests, unobserved source files, AST issues, synthetic line-zero observations, phase counts, saved child database count, isolated-pilot context evidence, and limitations.
- `provenance.json`: exact revision/base image, manifest and dependency-lock fingerprints, actual Python/SQLite/package/platform/environment versions, tracing/export tool hashes, reproduction command, index hash, and numeric-ID policy.

The executor also runs generated Python whose code filename is the expression text, not a real file. These observations are retained in `unbacked_execution` with their canonical test/shared sets and counts. They are not fabricated into source paths or discarded. Their real generator/evaluator/helper execution is separately line-traced where it runs in repository files. The audit's `raw_trace_complete` flag concerns readable saved shards; it does not claim exhaustive behavioral coverage. Any unreadable child shard is reported explicitly and sets that flag false, requiring a global conservative fallback in Stage 4.

`test_sets[s]` contains sorted inclusive ranges of offsets into `tests`; `shared_sets[s]` uses the same encoding for `shared_contexts`. Equal sets are interned once. Set zero is empty. File `lines` rows are `[first_line, last_line, test_set, shared_set]`, with inclusive endpoints. Consecutive lines with the same two sets are merged. Function, async-function, and class definitions record qualified name, AST kind, start/end line (including decorators), and the unions of test/shared sets observed anywhere in that source range. Nested definitions have their own ranges. Lambdas/comprehensions remain line-indexed within surrounding ranges rather than receiving invented names.

Every Python file in the clean checkout is indexed, including unexecuted files with empty observed maps. An unexecuted file is not considered irrelevant. SQL/CSV/config and other non-Python data do not have execution-line maps. The independent validator checks manifest identities, set indices/range encoding, every path/hash/line bound, AST-derived ranges, and each definition's aggregated coverage against its line records. Source syntax errors, if any, are reported rather than fabricating ranges.

## Safety limits for Stage 4

These maps record observed execution, not a complete dependency proof. A missing test/line relationship cannot establish that a mutation is harmless. In particular:

- Changes affecting import-time/global shared lines or child-process evidence should include all incoming tests unless independently justified by additional clean-source dependency evidence.
- Shared-fixture changes should include all recorded consumers; missing/uncertain consumers require all tests. Shared caches and global mutable state can make later tests depend on earlier execution. Use the supplied class/file cohorts to widen candidates, and fall back to all tests when cross-cohort state is uncertain.
- New/deleted files or definitions, added control-flow paths, decorators/metaclasses, fixture/config/data changes, unsupported/non-Python paths, and uncovered code need conservative handling. Do not interpret a zero-coverage change as safe to skip.
- Preserve incomplete tests as mandatory candidates. A collection error, test failure, unexpected skip, missing call/phase evidence, unmatched identity, or AST failure must not silently remove tests from consideration.
- Native DuckDB/numpy/pandas/SQLite internals are not Python line-traced. Platform, dependency, environment, or manifest differences invalidate assumptions and require revalidation/fallback.
- Generated/unbacked Python has no direct source-line correspondence. Changes to its generation/evaluation or uncertain embedded dependencies require widening or all-test fallback; do not treat its absence from physical source paths as missing execution.
- Process-worker/task attribution is intentionally coarse. Abruptly killed processes or environment changes that defeat instrumentation could lose observations; the completed audited runs saved child coverage and reported clean exits, not an exhaustive guarantee for future code.
